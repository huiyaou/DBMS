# 项目完成报告
项目名称：问卷工坊  
项目阶段：第二阶段 需求变更与功能完善  
技术栈：Python、FastAPI、PyMongo、MongoDB、HTML、CSS、JavaScript
github：https://github.com/huiyaou/DBMS.git

## 一、项目目标

本项目实现在线问卷的创建、发布、填写和结果查看。第一阶段已完成账号管理、四类题目配置、条件跳转、答案校验及问卷内统计；第二阶段根据用户反馈，将原先随问卷创建的题目扩展为可独立管理、共享和复用的常用题目。

本阶段需要同时满足两个目标：一是降低重复编题和团队协作的成本，二是确保题目更新、删除或复用后，历史问卷与答卷仍保持原有含义。系统因此采用题目版本与问卷快照相结合的方式，并将发布后操作限定为追加新题。

| 需求 | 实现方式 |
| --- | --- |
| 保存与复用常用题目 | 独立创建题目，或从问卷编辑页保存；选定版本后加入问卷 |
| 将题目分享给其他用户 | 所有者按用户名共享，其他用户可选用并基于已有版本继续编辑 |
| 保护已发布问卷的原题 | 保留发布快照，禁止覆盖、删除或替换原题，允许末尾追加新题 |
| 查看历史及恢复旧内容 | 保留版本来源关系，可基于任意可用旧版本编辑并保存为新版本 |
| 多版本并存 | 各版本独立保存，不同问卷可使用不同版本 |
| 查看使用情况 | 查询当前用户拥有且引用该题的问卷 |
| 建立题库 | 支持创建、重命名、删除题库，以及选题、移除条目和切换版本 |
| 跨问卷查看单题统计 | 按具体版本汇总当前用户拥有的问卷答案，区分回答次数与参与人数 |

## 二、系统设计

### 2.1 总体架构

系统沿用浏览器、FastAPI 后端与 MongoDB 的三层结构。前端负责题目配置、选题和结果展示；后端处理认证、权限、版本来源、问卷状态及答案校验；MongoDB 保存业务数据，并通过结构校验和索引约束写入。

~~~text
浏览器
  注册登录 · 问卷管理 · 常用题目 · 版本管理 · 题库 · 填写与统计
                          │ HTTP / JSON / Cookie
                          ▼
FastAPI
  认证与权限 → 题目和版本服务 → 问卷快照与追加 → 答案校验与统计
                          │ PyMongo
                          ▼
MongoDB
  账号与会话 · 问卷与答卷 · 常用题目与版本 · 题库
~~~

### 2.2 模块划分

项目保留 Backend、Frontend、Test、docs 目录，在原有代码上扩展功能。

| 模块 | 主要文件 | 职责 |
| --- | --- | --- |

| 题目与题库 | Backend/question_routes.py | 题目共享、版本创建与删除、题库管理、问卷追加及跨问卷统计 |
| 输入与业务校验 | Backend/models.py、survey_service.py | 输入类型、配置完整性、问卷状态与规则检查 |
| 答题与结果 | Backend/answer_service.py、answer_routes.py、statistics_service.py | 路径重算、答案提交、填写记录和问卷内统计 |
| 数据库基础层 | Backend/config.py、database.py、mongo_schema.py、init_db.py | 连接、集合校验、索引与兼容性检查 |
| 前端交互 | Frontend/app.js、answers.js、library.js 及对应样式文件 | 问卷编辑、填写向导、题目与版本管理、题库和统计展示 |
| 测试 | Test/test_mongodb.py、test_api.py、test_answers.py、test_questions.py | 数据库、接口、答题及题目复用流程验证 |

### 2.3 主要操作流程

用户登录后可直接进入“题目与题库”新建题目，或在编辑问卷时保存常用题目。题目页与题库页分标签展示，版本区采用左侧列表、右侧详情的布局；用户选中版本后，可以加入问卷、编辑为新版本、加入题库或查看统计。

“加入问卷”通过弹窗选择自己的草稿或已发布问卷，不要求预先打开草稿。题库对每道题保留一个选定版本，切换题库版本只改变以后选题的配置，不自动修改已经复用该题的问卷。

先在独立 PowerShell 窗口启动 MongoDB，并保持运行：

~~~powershell

~~~

再打开一个窗口启动应用：

~~~powershell
cd "D:\学校\大三上\DBMS\大作业2"
python -m pip install -r Backend/requirements.txt
python -m uvicorn Backend.main:app --host 127.0.0.1 --port 8000
~~~

浏览器访问 http://127.0.0.1:8000/，注册账号后使用，无预设账号。默认数据库为 survey_system，连接地址为 mongodb://localhost:27017/。应用启动会检查数据库并初始化集合与索引，不清空已有数据。停止后端时在启动窗口按 Ctrl+C；修改后端代码后需要重新启动服务。

## 三、MongoDB 设计

沿用 users、surveys、responses、sessions；新增 questions、question_versions、question_banks。问卷继续保存题目快照和可选来源版本，旧问卷无需补充来源。

### 3.1 MongoDB 结构

| 集合 | 内容 |
| --- | --- |
| questions | 题目身份、所有者、共享用户和创建时间 |
| question_versions | 题目 ID、来源版本 ID、创建者、创建时间和题目内容 |
| question_banks | 所有者、名称及所选题目版本 |
| surveys | 原有题目快照；题库选题额外记录 source_question_id 和 source_version_id |

题目版本通过 ObjectId 引用父版本，历史版本不覆盖。题目内容包含题型、标题、选项和校验；必答与跳转属于问卷，选题后可在问卷中单独配置。发布后原有题目快照固定，题库更新不会改变原题；允许在末尾追加尚未包含的新题，且保持原有顺序与跳转规则。原有问卷无需新增来源字段即可读取；没有来源的旧题不会自动参与跨问卷统计。

### 3.2 校验和索引

所有集合应用 strict/error 的 JSON Schema。题目所有者、共享对象、题目版本所属题目、题库所有者分别建立查询索引；版本引用、用户权限和快照的一致性由服务层检查。初始化先检查旧数据，再创建或更新集合和索引，不删除现有文档。

### 3.3 统计和权限

跨问卷统计按具体版本，只汇总当前用户拥有的问卷中实际回答该题的提交；回答次数与去重参与人数分别计算，跳过题目不计入。共享题目不等于共享问卷答案。数字题包含 0，选择题按选项计算次数，版本之间不自动合并。

## 四、题目版本与问卷修改

### 4.1 题目版本的创建与编辑

题目身份用于关联同一道常用题的不同版本；版本保存题型、题干、选项和校验配置。版本编号从 V0 开始，后续为 V1、V2 等，并记录来源版本，因此既支持连续修改，也支持从旧版本创建分支。

例如，V0 将年龄范围设为 0～120，基于它可创建范围为 0～150 的 V1，也可再次基于 V0 创建其他配置的 V2。V2 的来源仍为 V0，不因创建时间晚于 V1 而被误认为来自 V1。

编辑界面将题目标题置于最上方并锁定，用户可以修改题型、选项和校验条件。前后端共同检查新版本标题与来源版本一致；如需更换标题，应新建题目。保存生成新版本，不覆盖旧内容。恢复旧配置也通过选中旧版本、编辑并保存完成，无须另设复制旧内容的恢复按钮。

### 4.2 版本与问卷快照

选题时，系统复制选定版本的内容，生成问卷内独立题目 ID，并记录来源题目与版本。必答、题目顺序和跳转属于具体问卷，不随常用题目版本直接复制跨问卷目标。

保存带来源的题目时，后端核对内容与来源版本是否一致，防止修改后的题目继续使用旧版本身份参与统计。草稿中修改题干、选项或校验后，前端解除原来源关联；需要继续作为常用题复用时，可保存为新题或创建新版本。

### 4.3 发布后问卷修改

发布后的原题内容、顺序和跳转规则固定。系统通过独立追加接口向问卷末尾加入新题，避免普通编辑请求覆盖原题。追加请求检查所有权、状态、题目来源和修订号，并拒绝同一道题的不同版本重复加入；已关闭问卷不能追加。

追加采用匹配修订号的原子更新。当两个请求基于同一修订号同时追加时，仅一个成功，另一请求返回冲突，由用户重新读取问卷后再操作。

新追加的题目默认非必答，已有答卷不补填。原有跳转仍然执行，因此部分路径可能提前结束而不经过追加题；系统不会为提高新题覆盖率而改写旧题规则。

### 4.4 删除与引用保护

整题删除从常用题目列表移除该题，并清理所有题库中的对应条目；单版本删除只移除该版本及题库中引用它的条目。两类操作均不修改草稿、已发布问卷中的复用快照或已有答卷。

后台采用归档标记保留历史文档，前端直接隐藏已删除版本。删除当前版本后自动选中其他可用版本；全部删除时显示空状态。其他版本的编号、来源关系及问卷引用均不改变，重复删除同一有权限对象仍返回成功。

## 五、权限、校验与统计

### 5.1 权限边界

| 操作 | 权限规则 |
| --- | --- |
| 查看、选用题目及创建新版本 | 题目所有者或获共享的用户 |
| 共享、删除整道题目 | 题目所有者 |
| 删除某个版本 | 题目所有者，或该版本的创建者 |
| 管理题库、追加或管理问卷 | 对应题库或问卷的所有者 |
| 查看题目使用情况和跨问卷统计 | 仅返回当前用户拥有的问卷范围 |

题目共享只开放题目的复用能力，不共享问卷或答卷。页面是否显示按钮只是交互提示，最终权限由后端检查，不能通过直接请求接口绕过。

### 5.2 输入和来源校验

系统在前端、请求模型、后端业务和数据库四个层次检查输入。主要检查题型对应的字段、选项完整性、上下界、版本归属、父版本存在性及问卷状态。创建新版本时校验标题固定，选题与追加时校验来源权限；保存带来源的快照时检查内容一致性。

原有答题流程继续由后端校验答案，并根据配置从首题重算路径。跳过的必答题可不填，路径外残留答案会被拒绝；数字 0 保留为有效答案。登录异常、无权访问、状态冲突与输入错误分别返回相应状态码，便于页面提示和测试定位。

### 5.3 统计口径

跨问卷统计以“同一题目的具体版本”为单位，只汇总当前用户拥有且引用该版本的问卷。不同版本可能具有不同题型、选项或范围，因此不直接合并答案。没有来源信息的旧问卷不会仅凭题干相同自动纳入。

统计分别计算有效回答次数和去重参与人数；同一人多次提交可增加回答次数，跳过题目不计入有效回答。选择题按选项统计被选次数，多选题的选项次数之和可能超过回答次数；数字题计算包含 0 的平均值，文本和数字答案同时提供内容展示。无数字回答时均值为空，不用 0 代替无数据。

## 八、遇到的问题

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| P01 | 初次测试时默认 MongoDB 服务未运行 | 数据库测试类因连接失败无法启动 |
| P02 | 题目改动后仍可能携带旧版本来源 | 不同含义的答案可能混入同一版本统计 |
| P03 | 整份问卷发布后完全锁定，不能追加新题 | 原有实现不能满足后续选题需求 |
| P04 | 题目删除与问卷内题目删除的范围容易混淆 | 可能误解为复用题目与答卷也应移除 |
| P05 | 页面加载了新代码，后端仍运行旧进程 | 点击删除返回 Not Found，接口尚未加载 |
| P06 | 已删除版本继续显示，来源和编号又需要保留 | 删除反馈不直观，直接物理删除又会破坏历史关系 |

## 九、解决方式

| 编号 | 处理方式 | 验证依据 |
| --- | --- | --- |
| P01 | 使用临时 MongoDB 数据目录启动独立服务后重新测试 | 后续全量测试和模块测试正常完成 |
| P02 | 核对来源权限与快照内容，草稿修改后解除原关联；常用题修改生成新版本 | 来源篡改拒绝、版本与统计隔离用例通过 |
| P03 | 通过独立接口只追加新快照，用修订号限制并发更新 | 发布后追加、重复追加、关闭状态和并发用例通过 |
| P04 | 整题或版本采用归档删除，仅清理对应题库条目，明确操作提示 | 删除范围、快照与答卷保留用例通过 |
| P05 | 对照运行服务的 OpenAPI 定位旧后端，重启对应服务 | 两个删除接口均已加载，健康检查成功 |
| P06 | 前端过滤已删除版本，后台保留历史文档和来源映射 | 脚本语法检查通过；编号与来源不随显示列表重排 |
