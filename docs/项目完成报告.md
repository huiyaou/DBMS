# 基于 MongoDB 的问卷系统项目完成报告

项目名称：问卷工坊  
阶段：第一阶段——初始需求设计与实现  
报告日期：2026 年 10 月 21 日  
技术栈：Python、FastAPI、PyMongo、MongoDB、HTML、CSS、JavaScript

## 一、项目目标

本项目实现一个在线问卷系统，使用户能够创建问卷、配置题目和规则、发布填写链接、收集答案并查看统计结果。项目围绕 MongoDB 数据建模、配置驱动的业务逻辑、输入校验和可复现测试展开。

| 目标 | 已实现的功能 |
| --- | --- |
| 账号管理 | 注册、登录、退出、登录状态保持 |
| 问卷管理 | 创建草稿、编辑内容、查看自己的问卷、发布、调整截止时间、关闭 |
| 题目配置 | 单选、多选、文本填空、数字填空，题目排序、选项编辑和必答设置 |
| 校验配置 | 多选数量、文本长度、数值范围、整数限制 |
| 条件跳转 | 根据单选、多选和数字答案选择后续题目或结束填写 |
| 答案收集 | 链接访问、逐题填写、返回修改、提交前检查、保存完整答案 |
| 填写策略 | 多人同时填写、匿名提交、按设置允许同一账号多次填写 |
| 结果查看 | 全卷和单题统计、选择次数与人数、填空内容、数字平均值、填写记录 |

所有业务数据和登录会话存储在 MongoDB 中。题目、校验和跳转规则由创建者配置并保存为文档，后端读取配置执行。

## 三、MongoDB 设计
完整设计说明见 [MongoDB设计.md](MongoDB设计.md)。

### 3.1 集合划分与关系

| 集合 | 文档单位 | 关键字段 |
| --- | --- | --- |
| `users` | 一个用户 | `_id`、`username`、`username_key`、`password_hash`、`created_at` |
| `surveys` | 一份问卷 | `owner_id`、标题、状态、`draft_revision`、`share_code`、`settings`、`questions` |
| `responses` | 一次成功提交 | `survey_id`、`respondent_id`、`is_anonymous`、`attempt_key`、`answers`、`submitted_at` |
| `sessions` | 一次登录会话 | `token_hash`、`user_id`、`created_at`、`expires_at` |

`surveys.owner_id` 引用用户；`responses.survey_id` 引用问卷，`respondent_id` 引用填写者；`sessions.user_id` 引用登录用户。文档之间使用 BSON `ObjectId` 关联，时间使用 BSON `Date`，按 UTC 保存。

### 3.2 嵌入、引用与冗余选择

- 读取问卷时需要同时取得题目、选项和规则，将其嵌入 `surveys` 可以直接取得完整作答配置。题目数组的顺序就是默认答题顺序，题目和选项使用稳定 ID 关联。

- 填写记录随着提交持续增长，独立放入 `responses`，便于并发插入、分页读取和统计。一次提交整体写入一个文档，使全部答案一起保存。

- 用户信息独立保存，问卷和答案通过 ID 引用。答案保存题目 ID 和选项 ID，题目标题及选项文字由发布后的固定问卷定义提供。`username_key` 是为规范化登录和唯一性检查保留的查询字段。

### 3.3 Schema 和索引实现

`Backend/mongo_schema.py` 定义四个集合的 `$jsonSchema` 和索引，`Backend/init_db.py` 创建集合或通过 `collMod` 更新校验，使用 `strict/error` 检查写入。初始化先检查已有文档是否满足结构，满足后应用校验与索引；旧格式文档由迁移流程处理。

| 集合 | 索引 | 作用 |
| --- | --- | --- |
| `users` | `username_key`，唯一 | 等价用户名去重、登录查询 |
| `surveys` | `share_code`，唯一 | 分享访问与访问码去重 |
| `surveys` | `owner_id + created_at` | 创建者的问卷列表 |
| `responses` | `survey_id + submitted_at` | 问卷记录查询与统计筛选 |
| `responses` | `survey_id + respondent_id + attempt_key`，唯一 | 填写次数控制和请求去重 |
| `sessions` | `token_hash`，唯一 | 登录会话查询 |
| `sessions` | `expires_at`，TTL | 过期会话清理 |

## 四、跳转设计

### 4.1 规则数据结构

每道题的 `logic` 保存条件规则数组和默认目标。例如，“是否住宿”选择“否”时跳过宿舍设施题：

```json
{
  "rules": [
    {
      "id": "r1",
      "condition": {"operator": "eq", "value": "opt_no"},
      "target": "q3"
    }
  ],
  "default_target": "NEXT"
}
```

规则条件判断当前题答案。目标为后续题目 ID、`NEXT` 或 `END`。`NEXT` 表示下一题，最后一题的 `NEXT` 进入检查页；`END` 直接进入检查页，由填写者确认提交。

| 题型 | 条件操作符 |
| --- | --- |
| 单选 | `eq`：选中指定选项 |
| 多选 | `contains_any`：包含任意指定项；`contains_all`：包含全部指定项；`equals_set`：选择集合相等 |
| 数字 | `eq`、`gt`、`gte`、`lt`、`lte`、`between`，其中 `between` 包含左右边界 |
| 文本 | 使用默认目标 |

### 4.2 执行顺序

1. 校验当前题答案。
2. 按配置顺序检查规则，采用第一条满足条件的规则目标。
3. 未命中规则时使用 `default_target`；可选题未回答时也使用默认目标。
4. 进入目标题目，或进入提交前检查页。

保存配置时检查目标题目存在、目标位于当前题之后、选项引用有效、操作符与题型匹配。路径上的题目位置持续递增，因此能够结束。

### 4.3 返回修改与后端重算

前端允许返回修改答案。当修改使后续路径变化时，清理不再经过题目的旧答案。例如先选择“住宿”并回答宿舍设施，再改选“不住宿”，宿舍设施答案随路径变化移除。

提交时，`canonical_answers()` 从第一题开始，用问卷配置和提交答案重新计算路径，检查经过的题目，并生成按路径排列的答案。被跳过的必答题可不填；提交中包含路径外答案时返回 422。前端负责交互，后端负责最终路径与入库内容。

## 五、校验设计

### 5.1 分层校验

| 层次 | 检查内容 | 实现位置 |
| --- | --- | --- |
| 前端 | 当前题必答、长度、范围、选择数量，显示错误并定位题目 | `Frontend/answers.js` |
| API 输入模型 | 字段类型、枚举、数量和长度、日期时区、额外字段 | `Backend/models.py` |
| 后端业务 | 问卷配置、所有权、状态、实际路径、各题答案、匿名和重复策略 | `survey_service.py`、`answer_service.py`、`main.py` |
| 数据库 | 必填字段、BSON 类型、子文档结构、唯一性 | `mongo_schema.py` 中的 validator 和索引 |

### 5.2 草稿与发布校验

草稿允许保存空标题或尚未填写完整的题目，便于分步编辑。保存时检查 ID 唯一性、引用、规则形状和上下界关系。

发布时进一步检查问卷标题、至少一道题、题目标题、选择题至少两个有文字的选项、可满足的选择数量及整数范围，以及未来的截止时间。问卷最多 200 题，每题最多 50 个选项和 50 条规则；内容 BSON 编码最大为 8 MiB。

### 5.3 答案校验

| 题型或规则 | 校验方式 |
| --- | --- |
| 必答 | 实际路径上的题目必须提供有效答案 |
| 单选 | 答案为当前题已有选项 ID |
| 多选 | 答案为选项 ID 数组，检查重复、未知选项及最少/最多数量 |
| 文本 | 去除首尾空白，按 Unicode 码点计数，检查最短/最长长度 |
| 数字 | 检查有限数值、范围和整数限制，数值绝对值最多为 `9_007_199_254_740_991` |
| 可选未填 | 空白文本、空选择作为未回答，采用默认跳转 |
| 数字 0 | 保留为有效答案，参与数值统计 |
| 路径 | 检查未知题目、重复题目和路径外残留答案 |

后端完成全部校验后，将规范化答案整体写入 `responses`。答案错误返回 422，包含提示和相关题目 ID；页面显示对应错误，用户修改后重新提交。

### 5.4 提交状态与错误处理

新提交按读取到的问卷状态和受理时间检查开放资格，已受理请求继续完成保存；关闭或到期后受理的新提交返回 410。相同成功请求的重试返回原记录。

| 状态码 | 主要场景 |
| --- | --- |
| 401 | 未登录、会话过期、登录凭据错误 |
| 403 | 跨站写请求 |
| 404 | 对象不存在、无管理权限、问卷尚未发布 |
| 409 | 用户名重复、编辑冲突、重复提交内容不同、状态不允许操作 |
| 410 | 问卷关闭或截止 |
| 422 | 配置或答案校验失败 |
| 503 | 数据库暂时不可用 |

| P02 | 启动后端时 8000 端口已被已有服务占用，出现 WinError 10048 | 新服务无法监听同一地址和端口 |

| P04 | 答案校验需要区分空白、错误类型与数字 0 | 空值处理可能误拒绝有效的 0，或错误接受与题型不符的空值 |

### 8.2 实现中的设计难点

| 编号 | 难点 | 需要解决的情况 |
| --- | --- | --- |
| D01 | 修改前题答案后路径发生变化 | 已回答题目被跳过，旧答案需要清理 |
| D02 | 并发填写与网络重试 | 同一填写尝试可能同时到达后端 |
| D03 | 匿名与填写次数控制同时存在 | 展示时隐藏身份，系统仍需识别同一填写者 |
| D04 | 多次填写后的统计口径 | 提交份数、回答次数与不同参与人数需要分别计算 |
| D05 | 多页面编辑同一份草稿 | 旧页面可能覆盖新修改，发布时也需要检查对应内容 |

## 九、如何解决

| 编号 | 处理方式 | 验证结果 |
| --- | --- | --- |
| P01 | 根据本机版本使用 `InvalidHash`、`VerificationError` 处理密码验证异常 | 应用正常导入，注册、登录和错误密码测试通过 |
| P02 | 确认原服务已经监听 8000；需要重启时先在原终端 Ctrl+C，再运行启动命令。临时浏览器验收使用 8001 | 后续临时验收完成，运行说明补充重启方式 |
| P03 | 管理页“预览”用于检查布局，发布链接进入实际填写页，更新相应页面提示 | 浏览器完成从分享链接填写和提交的流程 |
| P04 | 按题型识别空答案，独立检查答案类型，使用缺失标记处理未回答 | 数字 0、空白文本、错误数组及错误数字类型测试通过 |
| D01 | 前端按新路径清理后续答案，后端从首题重算路径并拒绝路径外答案 | 返回改选浏览器验收与路径测试通过 |
| D02 | 设置填写尝试 UUID，后端确定去重键，使用复合唯一索引；重试比较原记录内容 | 并发冲突只保存一条，相同请求重试返回原记录 |
| D03 | 内部保存填写者 ID，记录接口按匿名标记选择公开字段 | 匿名记录字段过滤和重复填写策略测试通过 |
| D04 | 分别计算提交数量与去重账号数，按实际回答统计各题，数字均值包含 0 | 自动统计用例通过；浏览器结果为 2 份、1 人、均值 30 |
| D05 | 保存与发布匹配 `owner_id`、草稿状态及 `draft_revision`，成功保存时递增计数 | 旧计数请求返回 409，发布后的结构保持固定 |
